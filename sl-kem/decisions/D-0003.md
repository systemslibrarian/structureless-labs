Decision ID: D-0003 (sl-kem)
Question:     How should `sl-kem` bind parameter values for the first parameterized
              spec (SPEC-NNN)? Three families of approach exist; the lab must commit
              to one before any cryptanalytic work is honestly possible against the
              primitive.
Alternatives: (A) **Derive ourselves.** Run a lattice estimator with the lab's own
                  target security goals and cost model, produce a parameter set
                  bottom-up.
              (B) **Adopt-by-reference.** Pick a published, peer-reviewed
                  parameter set (FrodoKEM, ML-KEM, NewHope, etc.) and adopt it
                  verbatim with full attribution and an explicit non-endorsement
                  clause. The exploratory contribution of `sl-kem` then lies on
                  axes *other than* the parameter set itself — e.g. encoder
                  choice, error distribution variant, message space size.
              (C) **Hybrid.** Adopt a published set as a baseline AND independently
                  re-run the estimator under whichever cost model the lab cares
                  about, so the parameter binding has both the publication's
                  review history *and* a fresh estimator output.
Chosen:       **(B)** — adopt-by-reference for the first parameterized spec. (C)
              is reserved for after the lab has its own reference implementation
              under `sl-kem/ref/` and a working sl-bench harness that runs the
              estimator deterministically.
Reason:       The Cryptographer persona's mandate
              ([`sl-researchkit/personas/CRYPTOGRAPHER.md`](../../sl-researchkit/personas/CRYPTOGRAPHER.md))
              names the conservative default: *"reuse reviewed constructions."*
              Option (A) generates new parameters before the lab has a reference
              implementation to attack or an estimator workflow to trust —
              violating both the conservative-by-default principle (root
              README §Principles, item 1) and the anti-fabrication rule. Option
              (C) is the correct end-state but is blocked on infrastructure
              (`sl-kem/ref/`, an estimator runner in `sl-bench/sl-kem/`) that
              does not exist yet. Option (B) lets the lab make tractable
              progress today, with the right framing: SPEC-NNN's first
              parameter set inherits its security argument *from the chosen
              publication*, not from this lab; the lab's exploratory
              contribution is elsewhere.
Risks:        - A reader may take `sl-kem-NNN` as cryptographically equivalent
                to the publication it adopts from, even where `sl-kem` diverges
                on a non-parameter axis. Mitigated by SPEC-NNN's planned
                "Provenance" section, which will name the source publication,
                the exact spec version adopted from, and the axes (if any) on
                which `sl-kem` diverges.
              - A future D-0004 might pick a reference whose security argument
                later degrades. Mitigated by the fact that this decision binds
                the *framework*, not the reference — D-0004 (the choice of
                specific reference) is a separable decision and can itself be
                fossilized and re-decided.
              - "Adoption" risks credibility transfer toward `sl-kem` from the
                adopted construction. Mitigated by SPEC-NNN's mandatory
                non-endorsement language, mirroring the D-0002 (sl-researchkit)
                fence around `crypto-lab-scloud-vault` and S-Cloud+.
Evidence:     Grade D — framework decision; no numerical claim made here.

     borrows neither the publication's reference implementation nor its

     `sl-kem`. The two share a parameter set, not a security guarantee
