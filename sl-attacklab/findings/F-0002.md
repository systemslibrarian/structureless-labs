# Finding F-0002

Target:       `slff/spec/FORMAT-OVERVIEW.md` (draft) — specifically the rule:
              "Unknown **critical** fields → reject. Unknown non-critical fields →
              ignore + record."
Attacker:     Attacker persona (AI), acting on the break-it-first mandate from
              `sl-researchkit/personas/ATTACKER.md` (Mandate: "Listed the most
              plausible failure modes" and "Checked for unknown-critical-field and
              downgrade paths").

Hypothesis:   The slff format-overview spec asserts that unknown *critical* fields
              must be rejected and unknown *non-critical* fields ignored, but the
              spec does not define **how a field is marked critical versus non-
              critical**. Without a specified criticality marker — a bit, a flag,
              a `crit` list, a CBOR tag convention, anything — the rule is
              unimplementable as written. Two conforming implementations cannot
              consistently agree on which unknown fields are critical, which turns
              a stated security guarantee into an implementation discretion. An
              attacker who controls part of the container could insert a field
              that one parser treats as critical (and rejects) while another treats
              as non-critical (and silently accepts) — the classic
              accept-vs-reject divergence that has produced real-world failures
              in other formats (e.g. early X.509 v3 extension handling, JSON
              Web Token `crit` ambiguities).

Method:       Read `slff/spec/FORMAT-OVERVIEW.md` in full; searched the rest of
              `slff/` for any normative definition of the criticality marker.
              Findings:
                - Layout block names "Suite descriptor", "Crypto-agility block",
                  "Provenance (optional)" — none of these encode a way for *future*
                  unknown fields to declare criticality.
                - The rules block states the accept/reject behavior but not the
                  mechanism that signals criticality.
                - No CONTRIBUTING-style "how to add a field" guide exists yet
                  to imply a convention.
                - Compare baselines: X.509 v3 = per-extension `critical` bit;
                  JOSE (JWS/JWE) = `crit` array in the header listing critical
                  extension names; CWT = CBOR tag conventions + claim registration.
                  slff names none of these.
              Net: the spec's parsing-discipline claim depends on an implementation
              detail the spec does not specify.

Result:       **Inconclusive** — there is no test vector or reference implementation
              to attack. The finding is a **spec-readability gap** that, left
              unresolved, will become a real interoperability and downgrade-attack
              surface as soon as a second implementation exists.

Confidence:   90% that the spec as currently written does not define criticality
              (verified by inspection on 2026-06-09). 0% on whether any specific
              future implementation will compound the gap — that is for the next
              finding to test, against a concrete implementation.

Evidence:     Grade D — reasoned argument about spec state, not cryptanalysis.
              (Per `sl-researchkit/checklists/EVIDENCE-GRADING.md`: "Reasoned
              argument, untested" = grade D.)

Raised:       Open questions this finding surfaces, for the next decision review:
              - What concrete mechanism marks an slff field critical? (Per-field
                criticality bit? a `crit` list in the suite descriptor naming
                critical extension names? a CBOR tag convention?)
              - Does the AAD's canonical encoding need to cover the criticality
                listing as well as the field bodies? If not, the criticality
                listing itself is forgeable, which defeats the rule.
              - Should slff's "Unknown critical fields → reject" rule be enforced
                by a *positive* and a *negative* test vector in `sl-vectors`?
                The Engineer persona's checklist already requires negative
                vectors; this is a candidate.

Decision:     Recommended follow-up: a slff decision specifying the criticality
              mechanism (preferred starting point: the JOSE `crit` pattern, since
              it composes well with the suite-descriptor layout slff already
              uses), and a corresponding `sl-vectors` entry with two negative
              vectors — one for an "ignored-when-should-have-been-critical"
              case, one for a "rejected-when-should-have-been-non-critical"
              case.

Date:         2026-06-09
Status:       **Open** — spec-readability gap; no cryptanalysis attempted because
              no implementation exists yet. This is the honest state of slff on
              2026-06-09 and is the first finding *not* targeting sl-kem — evidence
              that the break-it-first gate scales across the lab.
