Hypothesis:   SPEC-000's `KeyGen` / `Encaps` / `Decaps` shape contains **seven

              or, worse, IND-CCA2-broken — variants. Each item is structural (no
              parameters needed to verify); each is independently fixable by a
              targeted SPEC-000 revision before any parameter-binding work in
              SPEC-001 begins.

Method:       Read SPEC-000 end-to-end against the FO-CCA2 reference construction (the
              Hofheinz–Hövelmanns–Kiltz framework, as instantiated in the Kyber and
              FrodoKEM specifications). For each step, asked: "What does an implementer
              have to *guess* that is not in the spec?" Every guess is a divergence
              opportunity.

## Issues filed

### F-0003-a — Undefined dimensions of `r`, `e'`, `e''`
SPEC-000 Encaps step 2 says `(r, e', e'') ← H(μ ‖ H(pk))`. The dimensions of `r`,
`e'`, `e''` are not stated. For `A^T · r` to type-check, `r` must be in `Z_q^m`
(or its analogue under whatever ring convention); `e'` must match `c_1 = A^T·r + e'`'s
dimension; `e''` must match `c_2 = b^T·r + e'' + E(μ)`. An implementer can infer
these by working backwards from the type signatures, but two implementers may pick
*different* inferred dimensions for `e''` (notably whether it is a scalar, a small
vector matching the encoder's output, or a vector of the same length as `c_2`).
**Severity:** high — divergence here breaks interoperation immediately.

### F-0003-b — `pk_hash` computation not specified in `KeyGen`
KeyGen step 5 says `sk = (s, pk_hash, ...)`. The text does not state how
`pk_hash` is computed. Decaps step 3 uses `H(μ' ‖ pk_hash)`, which only matches
Encaps step 2's `H(μ ‖ H(pk))` if `pk_hash = H(pk)`. The reader is expected to
infer this from the matching. An implementer who chose a different `pk_hash`
(e.g., a domain-separated hash) would still produce a self-consistent but
non-interoperating construction. **Severity:** medium — caught quickly by KAT
testing, but the spec should not depend on KAT testing for basic shape consistency.

### F-0003-c — `reject_key` source unspecified
Decaps step 5 returns `K = KDF(reject_key, H(c_1 ‖ c_2))` on rejection. The
spec does not say where `reject_key` comes from. Standard FO-CCA2 stores a
random `z` in `sk` during KeyGen and uses it as the reject key, ensuring the
rejection-path output is indistinguishable from a normal output by anyone
without `sk`. If an implementer interprets `reject_key` as a fixed constant
(or, worse, as some derivable value), the implicit-rejection property — and
thus IND-CCA2 — is broken. **Severity:** high — this is precisely the
class of FO mis-implementation the Hofheinz–Hövelmanns–Kiltz framework warns
about. KeyGen step 5's `(s, pk_hash, ...)` must explicitly include this `z`.

### F-0003-d — No domain separation between H uses
`H` is used in three structurally distinct roles: (i) `H(pk)` (pk hash), (ii)
`H(μ ‖ H(pk))` (FO derandomization producing `(r, e', e'')`), and (iii)
`H(c_1 ‖ c_2)` (passed into KDF for K derivation). Without explicit domain
separation tags, the same hash output could in principle be reused across
roles by an attacker who controls inputs to one role and observes outputs of
another. Modern KEMs (ML-KEM, FrodoKEM) tag each H call with a distinct
domain prefix or use a separate hash for each role. SPEC-000's `TODO` list
names "hash function and domain separation" generically; **this finding
calls out the specific risk so that the next decision (D-0005 or similar)
addresses it concretely rather than abstractly.** **Severity:** medium-to-high
— purely theoretical at the SPEC-000 stage, becomes load-bearing the moment a
concrete H lands in SPEC-001.

### F-0003-e — Encoder codomain / decoder domain dimensions implicit
Encaps step 4 computes `c_2 = b^T·r + e'' + E(μ)`, requiring `E(μ)` to be in
the same `Z_q^k` as `b^T·r + e''`. Decaps step 2 computes `μ' = D(v)`. The
encoder's output dimension `k` is not stated; it must be inferred. The
encoder choice TODO already exists, but the dimension question is separable:
even after picking `E`, an implementer needs to know whether `k = λ` (one
codeword per λ-bit message), whether the encoder operates over batches, etc.
**Severity:** medium — primarily an interoperation risk.

### F-0003-f — `s^T · c_1` typing in Decaps
Decaps step 1 computes `v = c_2 − s^T · c_1 (mod q)`. With `s ∈ Z_q^n` and
`c_1 ∈ Z_q^n`, `s^T · c_1` is a scalar. But the subtraction `c_2 − scalar`
only types if `c_2` is also a scalar (or the scalar broadcasts). If the
encoder produces a vector and `c_2` is therefore a vector, the formula needs
to be `v = c_2 − C_1·s` where `C_1` is a matrix derived from `c_1`. SPEC-000
elides this distinction. **Severity:** medium — could indicate either a
notation oversight (the spec means matrix-vector, not vector-vector) or a
genuine algorithmic difference from the FrodoKEM-style construction the
"family" line claims as the reference. Either needs resolving.

### F-0003-g — No statement of `A`-recovery from `seed_A`
KeyGen step 1 says `A ← uniform Z_q^{m × n}` (or a seed for A plus a
deterministic expander). Encaps step 3 says `c_1 = A^T · r`. If `pk = (seed_A, b)`
rather than `(A, b)`, Encaps must reconstruct `A` from `seed_A`, and the
spec must name the deterministic expander (and its domain separation tag).
SPEC-000 mentions the option but does not commit to either path or to the
expander identity. **Severity:** low — caught at the SPEC-001 binding step,
but listing it here so the resolution decision (D-0006 or similar) can name
the expander explicitly.

## Recommended follow-up

Open `sl-kem/decisions/D-0004.md` (the parameter-reference decision deferred
by sl-kem D-0003) and `sl-kem/decisions/D-0005.md` (a SPEC-000 revision
addressing F-0003) as separate decisions; the latter blocks SPEC-001. The
revision should:

1. State explicit dimensions for `r`, `e'`, `e''`, and `E(μ)` in the spec
   text (not merely in the parameter table). [F-0003-a, F-0003-e]
2. Add a KeyGen step computing `pk_hash = H_DS_PK_HASH(pk)`, where
   `H_DS_PK_HASH` is a domain-separated hash. [F-0003-b, F-0003-d]
3. Add `z ← uniform {0,1}^λ` to KeyGen and include `z` in `sk` as
   `reject_key`. Decaps step 5's `reject_key` is then `z` explicitly.
   [F-0003-c]
4. Introduce three distinct domain-separation tags for the three roles of
   `H`. [F-0003-d]
5. Resolve the scalar-vs-vector ambiguity in Decaps step 1 (likely by
   committing to the encoder's output dimension first, then rewriting the
   line). [F-0003-f]
6. Commit explicitly to `seed_A` vs. transmitted-`A`, and if `seed_A`, name
   the expander (likely SHAKE-128 with a domain tag). [F-0003-g]

SPEC-001 if revision plus parameter binding happen together — owner's
